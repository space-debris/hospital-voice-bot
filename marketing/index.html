Overview

What this product is built to handle

The project acts like a digital hospital front desk that can talk, listen, guide, verify, and execute operational tasks without pretending to be a doctor.

01

Hospital information at first contact

Patients can ask about OPD timings, departments, insurance, visiting hours, and emergency service details through conversational chat or voice entry points.

02

Verified patient workflows

After OTP verification, the assistant can move beyond public FAQs and help with appointment history, billing summaries, and report status checks tied to patient records.

03

Retrieval-grounded conversations

FAQ documents are indexed in ChromaDB so the assistant can answer from known hospital context instead of improvising facts when visitors ask operational questions.

04

Tool calling for real actions

The LLM is not only a text generator. It can trigger structured tools for doctor lookup, appointment booking, appointment cancellation, lab report checks, and billing retrieval.

05

Voice-ready service design

The original project supports Twilio-based incoming calls, speech loops, and barge-in, which makes the concept suitable for reception automation beyond the browser.

06

Guardrails for a sensitive domain

The assistant avoids diagnosis and treatment advice, protects guest access boundaries, and applies response safety checks before returning user-facing output.

How It Works

From patient message to safe, useful response

The assistant pipeline combines session state, retrieval, LLM reasoning, tool execution, and final response screening in a compact workflow.

Session-aware entry

User message arrives through chat or voice flow

A new or existing session is loaded first. That gives the system enough context to know whether the user is a guest or a verified patient before deciding what it is allowed to do next.

  • Tracks session identity and user type.
  • Keeps short conversation history for continuity.
  • Checks user input safety before downstream processing.

Knowledge retrieval

Relevant FAQ context is pulled from the hospital knowledge base

The RAG layer searches indexed FAQ chunks so operational answers stay tied to actual hospital information such as timings, departments, insurance, and visitor guidance.

  • Uses ChromaDB retrieval over markdown FAQ documents.
  • Returns context chunks with relevance scoring.
  • Restricts content by access level when required.

LLM plus tools

The model can answer directly or call structured backend tools

If the request needs a concrete system action, the LLM emits tool calls instead of guessing. Those tools route into appointment, department, report, doctor, and billing workflows backed by the database.

  • Gemini handles intent understanding and tool selection.
  • Tool router enforces guest versus verified access rules.
  • Database-backed actions return structured results for final phrasing.

Delivery layer

The final response is checked and delivered in natural language

After tool output is converted into a patient-friendly response, the system runs a final safety pass to keep advice boundaries intact and redact or limit sensitive details when needed.

  • Rejects unsafe medical-advice style behavior.
  • Protects guest views from sensitive data exposure.
  • Supports spoken output in the full voice-enabled version.

Experience Modes

Three ways the assistant creates value

The system is designed as a layered service experience, starting with simple guidance and expanding into verified operational support.

Public hospital support

Answer the questions a front desk receives all day

Ideal for website visitors who need quick hospital guidance before they commit to a call, visit, or login flow.

  • OPD timings, departments, insurance, directions, visiting hours.
  • Doctor and department discovery without exposing private patient data.
  • Clear prompts that guide users toward verified access when needed.

Sample prompt

"What departments do you have and when is OPD open?"

Assistant response style

Structured, concise, and grounded in hospital FAQ content rather than invented claims.

Authenticated service layer

Move from information to patient-specific action

Once the patient verifies through OTP, the assistant can act on their behalf across appointment, report, and billing workflows.

  • Book, cancel, or list appointments.
  • Check lab report readiness and result state.
  • Surface billing summaries in a conversational format.

Sample prompt

"Book me with the cardiologist tomorrow morning."

System behavior

The model decides whether to call search or booking tools and then turns the result into a natural language confirmation.

Telephony-ready concept

Extend the same assistant into incoming hospital phone calls

The broader architecture supports Twilio voice handling so the experience can move beyond web chat into a reception or helpline channel.

  • Speech-to-text and text-to-speech loop.
  • Auto-login for known callers where applicable.
  • Barge-in support for more natural phone interactions.

Tech Stack

The real stack behind the product story

This is not generic landing-page fluff. The sections below reflect the actual structure already present in the project.

Experience layer

Browser and channel interface

  • Static frontend written in HTML, CSS, and JavaScript.
  • Web chat client built around WebSocket messaging.
  • Browser speech features for voice input and spoken responses.
  • Twilio-compatible voice architecture for phone support.

Application layer

FastAPI orchestration and business logic

  • FastAPI backend with routers for chat, auth, and voice.
  • Session store and orchestrator controlling the request flow.
  • Tool router for appointments, reports, doctor search, and billing.
  • Health and metrics endpoints for runtime visibility.

Intelligence layer

Retrieval, reasoning, and controlled action

  • Google Gemini for conversation and tool calling.
  • ChromaDB retrieval over hospital FAQ documents.
  • Prompt-level role guidance and restricted capabilities.
  • Response safety checks before returning output to patients.

Data layer

Operational hospital data

  • SQLite with SQLAlchemy for seeded mock hospital data.
  • Doctors, departments, patients, appointments, lab reports, and billing records.
  • OTP-based verification for gated patient workflows.
  • Structured audit and metrics support in the backend.
Client layer Web chat and voice entry points

Patients begin through browser chat or telephony interaction.

Control layer Orchestrator, sessions, guardrails

Requests are routed, checked, and enriched with session context.

Knowledge layer RAG plus LLM tool calling

Answers are grounded, and structured actions are delegated to tools.

Execution layer Appointments, reports, doctor search, billing

Backend tools access hospital data and return results for final phrasing.

Launch Plan

How to present it now and how to evolve it later

The current recommendation is to ship this as a static showcase first, then reconnect the live assistant only when telephony and runtime services are ready again.

Best immediate move

Static product site

Host the `marketing/` directory as a static site. Use this page for outreach, portfolio visibility, founder decks, or product validation without ongoing telephony cost.

  • No live API or Twilio dependency required.
  • Fast global delivery and much lower maintenance.
  • Better message control than exposing a half-working demo.

Later evolution

Full production assistant

Reconnect FastAPI, telephony, and database-backed workflows when you are ready to operate a real service environment with budgeted third-party usage.

  • Move OTP and patient workflows behind secured production infrastructure.
  • Use persistent databases and managed secret handling.
  • Keep the public marketing site separate from the operational assistant.

FAQ

Questions this page already answers for a viewer

What does the project actually do?

It combines hospital FAQ answering, doctor discovery, appointment operations, report lookup, billing support, and patient verification into a conversational assistant.

Why not host the live demo directly?

The live experience depends on third-party voice infrastructure and runtime services. A static showcase is more reliable, easier to share, and more professional when some external pieces are currently offline.

Can this still be sold like a product?

Yes. In fact, this format is stronger for positioning. It explains value, architecture, capabilities, and operational fit without forcing every visitor through a brittle live demo.
